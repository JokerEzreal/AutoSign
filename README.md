# InstAtt 考勤系统 — 安全评估与负责任披露

> 本仓库记录的是对 **InstAtt 校园考勤系统**(诺丁汉大学马来西亚校区在用,Firebase 项目 `instatt-3c80d` + Microsoft Entra ID 身份认证)的一次独立安全评估。
>
> **目的**:把评估中发现的安全缺陷**负责任地披露**给校方 / InstAtt 团队,帮助其修复,并留下联系方式以便校方联系我们。
>
> **仅供学习与安全研究参考。本材料不包含规避操作步骤或可直接使用的绕过工具,也不鼓励、不支持任何伪造考勤或规避到场核验的行为。**

---

## 1. 系统背景(公开可观察的部分)

InstAtt 的考勤判定大致依赖三个要素:

- **时间窗**:教师在上课时段把课程"解锁"(`ongoingClasses` 中出现该课程)。
- **位置**:学生需连在教室 WiFi 下,客户端上报 WiFi 的 BSSID(MAC 地址)作为"人在教室"的证据。
- **身份**:通过 Microsoft Entra ID(Azure AD)登录,换取 Firebase 身份令牌后调用云函数签到。

> **评估方法**:本次评估通过**反编译 InstAtt 的 Android APK** 还原其客户端逻辑(OAuth 参数、Firebase 请求与签到字段等),并结合对其**公开 REST 接口的实际请求**进行交叉验证。

---

## 2. 安全发现

> 下列结论均为评估期间实际请求/测试得到;证据等级标注如下:`[实测]` 真实请求验证过,`[推断]` 基于机制推理,`[存疑]` 未完全确认。

### 2.1 Firestore 安全规则过宽:核心集合可匿名公开读取 `[实测]`

- `global/*`、`rooms/*`、`ongoingClasses` 这三类集合**无需任何认证**即可通过 Firestore REST 接口读取。
- 由此暴露的数据包括:
  - **实时已解锁课程**(课程代码、教室、授课教师、已签到人数)——任何人可实时监控全校哪些课在签到;
  - **全部教室配置**,包括**可绕过 WiFi 校验的教室**(`ignoreWifi = true`);
  - 允许签到的 **SSID 白名单**、系统阈值、版本信息等运营配置。
- 补充验证:普通学生登录令牌的读取权限与匿名几乎一致(仅能额外读取**自己**那一条学生记录);无法读取他人记录,说明问题集中在上述三类集合的规则过宽,而非账号越权。

**影响**:运营信息与课程/教室配置对公众无差别暴露。

> 实测抓取的公开数据样本见附录:[InstAtt_Database_Info.md](./InstAtt_Database_Info.md)(含当时的 `global`/`rooms`/`ongoingClasses` 返回内容)。该附录仅作为向校方披露的证据;其中含真实教师姓名等个人信息与签到请求格式,**公开发布前建议先脱敏**。

### 2.2 到场核验主要依赖可伪造的 BSSID `[实测/推断]`

- 签到请求把**客户端自报的 WiFi BSSID** 作为"在教室"的主要凭据。BSSID 属于可被客户端任意设置/重放的信息,单凭它**不足以证明设备物理在场**。`[推断:为网络身份固有性质]`
- 部分教室标记为 `ignoreWifi`(如 `DA05/DA07/NB03/NOLOC/ONLINE`),**完全跳过**位置校验。`[实测:见公开的 rooms 配置]`

**影响**:位置因子强度不足,存在被伪造到场的风险。

### 2.3 Device Code(设备码)OAuth 流程的滥用面 `[实测]`

- 该应用在 Entra 中是**公共客户端**;历史上可用**设备码流程**换取令牌。
- 目前校方/租户已对其**收紧**:设备码换取令牌返回 `AADSTS7000218`(要求客户端密钥),公共客户端无法满足——**这是正确的加固方向**。
- 设备码流程本身是业界已知的钓鱼/滥用向量,建议以条件访问策略**明确禁用**。

### 2.4 建议复核:Azure → Firebase 的令牌交换云函数 `[存疑]`

- 存在一个云函数用 Microsoft Graph 访问令牌换发 Firebase 自定义令牌。建议校方复核其对**调用方应用(appid)与令牌受众(aud)的校验**,避免官方 App 之外的客户端复用同一条链路。

### 2.5 客户端无代码混淆,敏感配置/密钥明文硬编码 `[实测]`

- 该 APK **未做代码混淆**:反编译后自有包 `instatt.instatt.*` 共 109 个类,全部为有意义的可读类名(0 个单字母混淆类名),无应用级 ProGuard 映射,源码可直接还原。
- 敏感配置与密钥**明文硬编码**在客户端,反编译即可提取,例如:OAuth `client_id`、回调地址、`resource`,以及一个嵌在 URL 中的 **Azure Function 调用密钥**(`?code=…`)。
- **影响**:大幅降低逆向与伪造请求的门槛;硬编码的服务端密钥一旦被提取即等同泄露,需作废并轮换。

### 2.6 客户端侧校验可被运行时插桩绕过(缺乏运行时完整性保护) `[实测/推断]`

- 到场/签到的关键判断发生在客户端(如 BSSID 比对、解锁状态处理),而 InstAtt **自有应用代码未实现任何运行时完整性保护**:`[实测:在 instatt.instatt.* 包与 AndroidManifest 内未发现相关调用]` 无 Root / 调试器 / Hook 检测,无签名校验,无 Play Integrity / SafetyNet / 设备证明。
- 结合「无代码混淆」(见 2.5),客户端逻辑与其上报的数据可被通用运行时插桩框架(Xposed/Frida 这类)在不触发任何防护的情况下修改。
- **影响**:凡仅在客户端执行的校验都不可信;单靠加固客户端也无法根治——到场判定必须在**服务端**完成,并以不可被客户端伪造的信号为依据。

## 3. 修复建议

- **Firestore 规则**:对 `rooms` / `global` / `ongoingClasses` 增加认证与最小权限;敏感运营字段不下发到客户端;教室 BSSID 等核验数据不应对客户端可读。
- **到场核验**:不要仅依赖客户端上报的 BSSID。结合服务端信号综合判定,例如:严格时间窗 + 随机化质询、设备证明(device attestation)、教师端在场确认、可信定位信号;核验所用的 BSSID 应保存在服务端且不可被客户端读取。
- **设备码流程**:以条件访问禁用或限制(目前已部分实施)。
- **云函数**:严格校验入站令牌的 `appid` / `aud`,限定为官方客户端。
- **客户端加固**:启用代码混淆(R8/ProGuard);不要在客户端硬编码函数/服务端密钥,改用服务端代理或短时令牌;上述已暴露的 Azure Function `code` 应作废并轮换。
- **信任边界**:不要信任任何仅在客户端执行的校验结果;到场判定与其依据(位置/设备)须在服务端核验。运行时完整性(Play Integrity / 设备证明)、Root/Hook 检测可作为纵深防御叠加,但**不能替代**服务端校验。
